# Signature fixtures

Source data: goempo's repository, `internal/types/testdata/txs.jsonl`, with provenance in its adjacent README. These are transaction envelopes recorded on 2026-11-17 from `https://rpc.tempo.xyz` and `https://rpc.moderato.tempo.xyz`, paired with RPC `from` and receipt `keyId`. No Go source was read or used.

- `signature-mainnet-moderato.json`: all fifteen Tempo transactions in that corpus, spanning untyped secp256k1, P256 and WebAuthn approvals, keychain V1/V2, sponsorship, key authorization, and AA authorization lists. Each entry retains the source network, block, variant label, raw signature, reconstructed unsigned transaction preimage, and independently recorded RPC sender/key ID. Embedded authorizations are retained as exact RLP bytes.
- `signature-p256.json`: the primitive P256 approval extracted from the moderato block 4688660 V1 keychain fixture. V1 uses the original transaction signing hash, so its inner signature is also a valid standalone P256 fixture. Its expected sender is the original independently recorded RPC key ID.
- `signature-eip7702.json`: the six-field authorization from the moderato block 4063501 type-4 transaction; the file retains the source transaction hash. Used to compare Ethereum and Tempo authorization wire formats. This corpus does not independently record that authorization's authority, so this particular test is a wire-equivalence assertion, not an independent sender oracle.

Unsigned preimages were reconstructed from decoded envelope fields following `~/dev/tempo/crates/primitives/src/transaction/tempo_transaction.rs`, `SignableTransaction::encode_for_signing`: omit the final transaction signature; replace the fee-payer signature with an empty string if absent, or byte `00` if present; omit the fee token commitment when sponsored; prefix the RLP list with `76`. Tests hash those preimages rather than using the transaction hash as a signing hash.

Implementation specification: `tt_signature.rs` (`PrimitiveSignature::from_bytes`, `recover_signer`, `KeychainSignature::signing_hash`, `verify_webauthn_data_internal`), `key_authorization.rs` (`signature_hash`, signed nested RLP and trailing optionals), and `tt_authorization.rs` (`signature_hash`, four-field wire format), in the same Rust reference checkout. The requested `authorization.rs` is named `tt_authorization.rs` there.

API: `recover-signature` returns the recovered sender plus an access-key ID only for keychain signatures. Invalid wire encodings or cryptographic approvals signal an error. `signature-kind` validates the wire shape and returns `:secp256k1`, `:p256`, `:webauthn`, `:keychain-v1`, or `:keychain-v2`. Keychain state authorization and hardfork-specific version admissibility belong to the caller; cryptographic recovery supports both historical versions. Configurable accounts are deliberately outside the T0–T13 scope. `key-authorization-signer` consumes the decoded nested `(authorization signature)` RLP list, canonicalizes trailing optional fields for hashing, and disallows keychain envelopes. `authorization-signer` accepts Tempo four-field and standard EIP-7702 six-field decoded RLP lists; both use `keccak256(05 || rlp(chain-id,address,nonce))`.
